# De MariaDB a PostgreSQL

Paso 2 de la versión multi-institución (ver [`MULTI-INSTITUCION.md`](MULTI-INSTITUCION.md)).
El sistema corre ahora sobre **PostgreSQL 18** y se comporta como sobre
MariaDB. Las diferencias que quedan están contadas abajo, una a una.

No incluye Row Level Security: eso es el paso siguiente.

## Levantarlo en local

Hace falta **PostgreSQL 18 o superior**. El esquema usa un cotejo ICU no
determinista y PostgreSQL acepta `LIKE` sobre él solo desde la 18. PHP necesita
`pdo_pgsql` (en el `php.ini`: `extension=pdo_pgsql`).

```bash
# 1. Un rol para la aplicacion, SIN superusuario (RLS lo necesitara asi),
#    y las dos bases con cotejo ICU.
psql -U postgres -c "CREATE ROLE matriculas LOGIN PASSWORD '...'"
psql -U postgres -c "CREATE DATABASE matriculas OWNER matriculas TEMPLATE template0 \
     LOCALE_PROVIDER icu ICU_LOCALE 'und' LOCALE 'C' ENCODING 'UTF8'"
psql -U postgres -c "CREATE DATABASE test_matriculas_mt OWNER matriculas TEMPLATE template0 \
     LOCALE_PROVIDER icu ICU_LOCALE 'und' LOCALE 'C' ENCODING 'UTF8'"

# 2. .env con DB_CONNECTION=pgsql y los datos de arriba (ver .env.example)

# 3. El esquema y una institucion
php artisan migrate
php artisan instalar
```

La migración `2026_10_02_100000_esquema_en_postgres` corre el guion
`database/sql/postgres/01-esquema.sql`. **El guion es la fuente de verdad** y
también se puede correr a mano:

```bash
psql -U matriculas -d matriculas -f database/sql/postgres/01-esquema.sql
psql -U matriculas -d matriculas -f database/sql/postgres/01-esquema.revertir.sql
```

Los dos son idempotentes: se pueden correr dos veces seguidas. La reversión
**se lleva los datos** y se niega si hay más de una institución.

### Las cuatro puertas

```bash
php vendor/bin/phpunit          # phpunit.xml ya apunta a pgsql / test_matriculas_mt
php vendor/bin/pint --test
php -d memory_limit=-1 vendor/bin/phpstan analyse
DB_DATABASE=test_matriculas_mt php database/verificacion_esquema.php --borrar-datos
```

La verificación del esquema **vacía la base**. Con `DB_DATABASE` en el entorno
apunta a la base de pruebas sin tocar el `.env`. Las dos barreras de siempre
(`APP_ENV=local` y `--borrar-datos`) siguen igual.

La carrera por el último cupo se prueba aparte, con dos procesos:

```bash
DB_DATABASE=test_matriculas_mt php database/verificacion_concurrencia.php --borrar-datos
```

## Pasar los datos de una base MariaDB

```bash
# En el .env, ademas de DB_* (PostgreSQL), los ORIGEN_DB_* (MariaDB)
php artisan migrate                        # el esquema, en una base vacia
php database/copiar_a_postgres.php         # copia
php database/comparar_motores.php          # compara
```

**`copiar_a_postgres.php`**

- Abre MariaDB en **solo lectura** (`SET SESSION TRANSACTION READ ONLY`).
- Copia tabla a tabla en el orden de las claves foráneas, con los ids de origen.
- Convierte los `tinyint(1)` a `boolean`.
- No copia las columnas generadas (las calcula PostgreSQL).
- Apaga los triggers durante la carga: el de cupo rechazaría matrículas hoy
  válidas de una promotoría cuyo cupo se bajó después de llenarse.
- Al final pone cada secuencia en el máximo de su tabla.

Todo va en una transacción. Se niega si el destino ya tiene datos. `--vaciar`
lo vacía antes, solo con `APP_ENV=local`.

**`comparar_motores.php`** compara cada tabla de dos formas:

1. **Conteo de filas.**
2. **Contenido**: la huella de cada fila con los valores normalizados, también
   las columnas generadas.

Un conteo que cuadra no basta: una fecha corrida una hora pasa cualquier
conteo. Las huellas se comparan ordenadas, así que no depende del orden en que
cada motor devuelve las filas. Sale con código 1 si algo difiere. La tabla
`migrations` no se compara: cada motor registra sus propias migraciones.

## Cambios de tipo

| MariaDB | PostgreSQL | Notas |
|---|---|---|
| `bigint unsigned AUTO_INCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY` | `BY DEFAULT` para poder copiar los ids; después `setval` al máximo |
| `bigint unsigned` (claves foráneas) | `bigint` | Un id nunca es negativo |
| `tinyint(1)` | `boolean` | 16 columnas. El PHP no comparaba contra 1/0: pasa por los casts de Eloquent |
| `tinyint unsigned` | `smallint` | Donde no había un CHECK más estrecho, uno nuevo `0..255` |
| `smallint unsigned` | `integer` + CHECK `0..65535` | |
| `int unsigned` | `bigint` + CHECK `0..4294967295` | |
| `int` | `integer` | |
| `varchar(n)`, `char(n)`, `text`, `mediumtext`, `longtext` | `varchar(n)`, `char(n)`, `text` | Todas con `COLLATE insensible` (ver abajo). Los `char` son tokens y un color de largo fijo: el relleno de PostgreSQL no cambia nada |
| `datetime`, `timestamp` | `timestamp(0)` sin zona | La aplicación guarda la hora local y así la lee |
| `time` | `time(0)` | |
| Columna generada `VIRTUAL` (`activo_marca`, `ranura_activa`) | Columna generada `STORED` | La única forma que admite un índice único. Misma regla, mismo nombre |
| `IF(c, a, b)` en columnas y CHECK | `CASE WHEN c THEN a END` | |
| `x regexp '...'` (CHECK del color) | `x COLLATE "C" ~ '...'` | Las expresiones regulares no admiten un cotejo no determinista |
| `ON UPDATE CURRENT_TIMESTAMP` (`restablecimientos_clave.created_at`) | Trigger `restablecimiento_al_dia` | Como en MariaDB: solo si la fila cambia y nadie toca la columna |
| Trigger de cupo con `SIGNAL SQLSTATE '45000'` | Función plpgsql y dos triggers, `RAISE ... ERRCODE '45000'` | Mismo estado, mismo mensaje, mismo `FOR UPDATE` |

Se conservan **todos los nombres**: tablas, columnas, claves foráneas, únicos,
índices, CHECK y triggers. PostgreSQL no crea solo el índice de una clave
foránea, así que se crearon a mano los que MariaDB tenía.

### El cotejo

MariaDB comparaba con `utf8mb4_unicode_ci`, que **no distingue mayúsculas ni
tildes**. De eso dependen cosas que no se ven:

- `Ana` entra como `ana`;
- el buscador encuentra «gomez» en «Gómez»;
- no pueden existir dos departamentos «Música» y «musica».

PostgreSQL distingue las dos cosas por defecto. El guion crea el cotejo ICU
`insensible` (`und-u-ks-level1`, no determinista) y lo pone **en cada columna
de texto**.

> **Una columna de texto nueva tiene que llevar `COLLATE insensible`.** Sin él,
> nada falla: el login empieza a distinguir mayúsculas y el buscador deja de
> encontrar nombres con tilde. `verificacion_esquema.php` vigila las tres
> columnas de las que depende (`username`, `nombre_completo` y el nombre de
> un departamento).

## Consultas traducidas

El código casi no tenía SQL de MySQL: lo de verdad estaba en el esquema.

| Antes | Ahora | Dónde |
|---|---|---|
| `SUM(condición)` (sumar un booleano) | `SUM(CASE WHEN condición THEN 1 ELSE 0 END)` | `EstadisticasController` (3), `EstadisticasDeProfesor` (3), `ResumenActividades`, `ResumenInstitucion` |
| `a <=> b` | `a IS NOT DISTINCT FROM b` | `EstadisticasDeProfesor` |
| `->having('marcadas', ...)` (alias en el HAVING) | `->havingRaw('COUNT(*) >= ?', ...)` | `EstadisticasController` |
| `pluck(DB::raw('COUNT(*)'), ...)` | `DB::raw('COUNT(*) as total')` | `AsistenciaDeActividad`. Cada motor bautiza la columna a su manera |

Todo lo demás (`DATE()`, `COALESCE`, `COUNT(DISTINCT)`, `whereDate`, `upsert`,
`lockForUpdate`) ya valía igual en los dos motores.

## Comportamientos del motor que cambiaron

**Una sentencia fallida inutiliza la transacción que la envuelve.** En MariaDB
se podía capturar el error y seguir consultando; en PostgreSQL, todo lo
siguiente falla con `25P02` hasta deshacerla. Los sitios que capturan un error
de la base y siguen trabajando aíslan ahora la escritura en su propio
`DB::transaction` (dentro de otra, un punto de guardado):

- `FichaController`: corregir promotoría y readmitir;
- `PanelGrupoController`: borrar un grupo;
- `RecursoController`: borrar desde cualquier catálogo.

Los otros cuatro ya lo hacían.

**Los errores se reconocen distinto** (`App\Support\ErrorDeBaseDeDatos`):

| | MariaDB | PostgreSQL |
|---|---|---|
| Clave única repetida | `Duplicate entry ... for key 'x'` | SQLSTATE `23505`, y el nombre entre `"x"` (o `«x»` con el servidor en español) |
| Fila en uso al borrar | código `1451` | SQLSTATE `23503` **y que la sentencia sea un `DELETE`**: PostgreSQL da el mismo estado a «sigue en uso» y a «apunta a algo que no existe» |
| Cupo agotado | `45000` + mensaje | igual |

Siempre se mira primero el SQLSTATE, que no depende del idioma.

**El reintento de conexión** (`App\Support\ConexionQueReintenta`) ya no decide
por código. Con `pdo_pgsql` **todo** fallo al conectar llega como `08006`,
también una contraseña mala (medido). Decide por el texto, y en Windows por el
número de Winsock (`/10061`), que no se traduce. `PDO::ATTR_TIMEOUT` sigue
funcionando: `pdo_pgsql` lo convierte en `connect_timeout`.

**La paginación con empates pierde filas.** `lazy()` pagina con
`LIMIT/OFFSET`, y si el orden tiene empates en el borde de una tanda, cada
consulta puede resolverlos distinto: una persona sale dos veces y otra
ninguna. Pasó en el informe de estudiantes con dos «Mariangel» de Danza
Folclórica, y la de 7 años **faltaba en la lista de su grupo**. MariaDB
acertaba por suerte con esos datos. Los dos informes que paginan llevan ahora
desempate por id, como ya lo llevaban Usuarios, Cancelaciones y los inscritos
de una actividad (`InformeTest::test_no_se_pierde_nadie_cuando_hay_nombres_repetidos`).

**Las secuencias no se mueven solas.** Insertar una fila con el id escrito a
mano no adelanta la secuencia, como sí hacía `AUTO_INCREMENT`. Lo tienen en
cuenta la copia de datos y los guiones de verificación (`ajustarSecuencias()`).

## Lo que NO es idéntico

1. **Los empates en listas recortadas, ya resueltos por nombre.** Cinco listas
   se ordenan por una cifra o una fecha y se recortan, y con un empate en el
   corte cada motor dejaba pasar a una fila distinta:
   - la vista previa de alertas de Gestión;
   - la bandeja de clases sin dictar (muchas comparten fecha);
   - la de posibles abandonos;
   - «Profesores con más clases»;
   - «Estudiantes más constantes».

   **Decisión del usuario (01/10/2026): entre empatados, por nombre.** Vive en
   `App\Support\OrdenPorNombre`, que compara como la base, sin mayúsculas ni
   tildes: con `intl` usa el mismo cotejo ICU; sin `intl` quita tildes a mano.
   Así que ahora salen **siempre** las mismas filas, aunque no siempre las que
   enseñaba MariaDB, cuyo orden de empates tampoco estaba garantizado.

   Sin tocar, porque no se recortan: el desplegable de grupos de Usuarios y las
   filas de Horarios enseñan las mismas líneas, a veces en otro orden.
2. **Caracteres fuera del plano básico** (emojis, letras «bonitas» como
   «𝕄𝕒𝕣𝕚𝕒»). `utf8mb4_unicode_ci` les daba a todos el mismo peso: los ordenaba
   al final y los trataba como iguales entre sí. ICU los lee como lo que
   parecen: «𝕄𝕒𝕣𝕚𝕒» se ordena y se compara como «Maria».
3. **Espacios al final.** MariaDB los ignoraba al comparar (`'a' = 'a '`);
   PostgreSQL no.
4. **Las pruebas tardan más en Windows**: 6:38 frente a 3:00, repartido por
   igual (mediana de 0,2 s por prueba). Una parte es la conexión (42 ms frente a
   15 ms aquí, porque PostgreSQL abre un proceso por conexión). No dice nada del
   servidor, que será Linux.

## Cómo se comprobó

- **Datos:** el volcado de producción migrado (base `matriculas_multitenant`),
  copiado de MariaDB a PostgreSQL. **Las 36 tablas coinciden en filas y en
  contenido** (13.235 filas), columnas generadas incluidas. El comparador se vio
  fallar alterando un booleano y una fecha.
- **Secuencias:** las 30 quedan por encima del máximo de su tabla.
- **Esquema:** subido y revertido dos veces seguidas. El `pg_dump --schema-only`
  final es idéntico al de la primera subida.
- **Suite completa, en verde.** Cada prueba reescrita o nueva se vio fallar
  quitando su arreglo:
  - el reconocimiento de errores, cuatro mutaciones;
  - el reintento de conexión, cinco;
  - el índice de los inscritos, quitándolo;
  - el desempate del informe, quitándolo.
- **`verificacion_esquema.php`:** 48 de 48. Las garantías nuevas (cotejo y
  trigger de `restablecimientos_clave`) se vieron fallar.
- **Concurrencia del cupo:** la segunda inscripción espera en el `FOR UPDATE` y
  se rechaza. Sin el `FOR UPDATE`, hay sobreventa.
- **Los informes**, generados como administrador con el código de antes sobre
  MariaDB y con este sobre PostgreSQL:
  - el de actividades sale idéntico byte a byte;
  - el de institución y el de estudiantes, con las mismas filas y otro orden
    entre empates.
- **Las pantallas con más SQL propio**, generadas igual en los dos motores:
  - Panel, Programas, Fichas incompletas, la lista de actividades y tres fichas
    de actividad salen idénticas;
  - las demás, ver [Lo que NO es idéntico](#lo-que-no-es-idéntico). Con el
    desempate por nombre, Gestión, Estadísticas y Cancelaciones salen iguales
    en dos pasadas seguidas.
- **En el navegador:** entrar escribiendo `ADMIN` en una cuenta `admin`, y las
  pantallas de la institución 2, que siguen aisladas de la 1.
